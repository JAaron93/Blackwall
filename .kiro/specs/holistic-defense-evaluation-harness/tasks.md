# Implementation Plan: Holistic Defense Evaluation Harness

## Overview

This plan implements the harness in `design.md` against `requirements.md`, in the design's four phases. Phase 1 is the pure library (including the Findings_Module `findings.py`, the Report_Module `report.py` and the dollar-cost computation `billing.py`), the Corpus_Loader `corpus.py`, the Egress_Guard `egress.py` (installed from the first `stages` run, with an empty Runtime_Hosts for every offline subcommand), the observers, the offline stage pass, the Composer with its differential test and the Identity_Check, and the Run_Set schema and the Run_Store with its create and append rule (`stages` alone creates a Run_Set; every later subcommand opens it for append first). Phase 2 adds the run protocol, the live whole-system and Forced_Table runs, the TASK-F06 finding from the Whole_System_Runs, the comparison notebook, the recompute tests and the mutation guard. Phase 3 adds the optional layers (IOC corpus, threat intelligence, CBM fixture, W3 to W5), the CBM_Probe_Step `cbm_probe.py` and the LX-wave support. Phase 4 adds the band study, the recommendation gate, the cross-link cell and the ADR.

Task ids are the numbers below (for example 6.1). The repository convention of a "Dependencies:" line and a requirement reference is kept inside each task. Requirement references use `X.Y` for requirement X, criterion Y. "Validates" lines cite the numbered correctness properties of `design.md`.

## Conventions that apply to every task

- Strict TDD (repository rule): write the named failing test or reproduction first and watch it fail with an assertion that names the missing behavior (Requirement 30.1, 30.2), then implement.
- Every commit goes to a feature branch only. No task pushes, merges, or commits to `main` or `master`. Before staging, check that no `.env` file, key, credential or `.sqlite` WAL file is in the payload.
- No task edits, creates, prints or reads a real `.env` file. A live credential is read only after the human names that variable in the current conversation (Human_Grant), from the environment of the child process, never logged or written.
- No task executes, imports or fetches a payload. Payloads are inert strings.
- No task changes `src/` outside `src/blackwall/holistic_eval/`, except the conditional task 5.3. No task edits `AGENTS.md`, `.agents/rules/` or `.greptile/`. The spec-list entry in `AGENTS.md` landed with the spec itself, and the two rule proposals are documents prepared in the Caught_Module task (1.2) and applied only after maintainer approval.
- Property tests use Hypothesis with at least 100 examples, strategies that generate valid values only, and no more than 50% discards. Async BDD steps use `run_async`, and background tasks are flushed in the same coroutine as the scheduling call (rules 2, 13, 16, 75).
- Every property test, every BDD scenario and the `LX-wave` support are required sub-tasks. The only experiment that is optional is running `LX-wave` itself, which happens only when the maintainer explicitly requests it (Requirement 17.25).
- Live and grant-gated tasks say so, name the variable, and stay unchecked with a deferral note until a measured Run_Set exists (rule 74, Requirements 22.10, 22.11). They are never simulated, stubbed or mocked to claim acceptance.
- Module placement follows the design's file-layout table, which names a module for every piece of work (design Q18). Each task names its module, and no task invents one.
- Every Harness invocation (`plan`, `stages`, `run` and `validate`) installs the Egress_Guard of `egress.py` (task 3.4) with that invocation's Runtime_Hosts before any client is built, and every live or grant-gated task depends on task 3.4.
- A Run_Set is created only by the `stages` subcommand, through `store.create_run_set` (task 2.3), which refuses an existing directory. A live `run`, `run --experiment LX-wave` and `probe-cbm` call `store.open_for_append` (task 2.3) before any client is built, any call is made or any record is written, and only append: no task overwrites or deletes an existing per-case record, run entry, `cbm_fixture` entry or Probe_Attempt. A Manifest's `cbm_fixture` entry is created only by `RunSetAppender.bind_cbm_fixture` (task 2.3), which the first fixture-backed `run` (task 22.8) or the first `probe-cbm` (task 22.7) calls and every later one uses to verify the recorded fixture digests.
- Figures are built once: `report.py` builds the report structures and `findings.py` the findings report. The CLI prints them and the Notebook renders them, and neither recomputes a figure. Only the `stages` and `validate` subcommands call the findings computation; the Notebook renders the stored report through `format_findings` only.

Boundary tests, each written first: (1) one eligible attack case id submitted repeatedly (enough repeats that the repeated count would reach 30 attack cases) is rejected as `INPUT_INTEGRITY`, counts nothing and does not pass the count check; (2) one eligible benign case id submitted repeatedly is rejected the same way and does not pass the benign count; (3) an id listed more than once inside one Authoring_Record is rejected; (4) an id listed in two Authoring_Records is rejected and counted under neither; (5) a rejection for any duplicate has `INPUT_INTEGRITY` as its only failed check, zero counted cases, each duplicated id named with its kind, and no other check evaluated; (6) every submitted, counted and excluded total counts distinct case ids (30 distinct eligible ids of each class pass, and 29 distinct plus a repeat of one of them fails); (7) the rejection records the exclusion report, listing each distinct submitted id as not counted at level `submission`, naming the duplicates, with per-class totals; (8) a case id that no record lists has no known class and is reported as `unclassified` and excluded.
